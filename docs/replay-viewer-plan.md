# 客户端外录像观看：可行性与执行方案

调查日期：2026-10-27。本文是实施建议，尚未实现或验证播放器原型。

## 结论与建议

**可行：在现有 Windows 程序内做独立的二维战术回放**，包括播放、暂停、倍速、拖动时间、地图平移缩放、跟随英雄和点击事件跳转。画面是基于录像数据重建的战术视图，不是 Dota 2 的游戏画面。推荐先完成这一版本。

**客户端级三维画面及完整观战功能，无法依据现有证据承诺可行或等价。** `.dem` 可解析出实体和事件，但解析器不是 Source 2 渲染器；还需要地图、模型、动画、粒子、音频、材质、游戏逻辑和版本匹配。自由移动一个自制相机相对可行；玩家原始镜头、完整迷雾、技能表现和逐帧一致性都需要逐项验证，不应把“数据可解析”当作“可完整还原”。[Clarity](https://github.com/skadistats/clarity) 列出了实体、事件、部分镜头相关消息等数据，但没有承诺复原所有玩家视角。

| 路线 | Dota 是否运行 | 得到的体验 | 判断 |
| --- | --- | --- | --- |
| 独立二维回放 | 不需要 | 地图、单位标记、时间轴、平移缩放、跟随与事件 | 推荐，现有项目可扩展 |
| 启动 Dota 观看 | 需要 | 客户端原生画面和它支持的观战功能 | 作为可选跳转；程序内嵌、自动定位、同步控制均需单独验证，不能视为已有接口 |
| 独立三维重建 | 不需要运行客户端，但可能需要本地资源 | 自制画面与相机，复原程度不确定 | 高成本探索，不列入首版承诺 |

固定机位视频可作为原画面的补充，但视频不能任意更换视角，不能替代交互回放。

## 项目现状与数据边界

- `dota_review/ingest.py` 从 gem-dota 获取英雄位置，按整数游戏秒去重；`storage.py` 的位置主键也按秒。`entities.py` 对小兵和野怪每 2 秒采样。两者不能提供客户端级连续运动，插值只是视觉估计。
- `app.py` 已有 Tkinter Canvas、时间滑块、实体和事件叠加；现有地图资产和坐标转换需先实测校准。项目 README 明确现有底图不保证真实地形、视野及通路。
- 导入时保存 `replay.dem` 的路径，可为单场比赛增加独立回放缓存；已导入比赛需要提供重新生成缓存入口，不能假设旧 SQLite 保存了新回放所需的 tick 级数据。
- 现有游戏时间采用暂停感知的 GameClock。游戏秒在暂停期间可能对应多个 tick，不能只用整数秒作为唯一播放坐标或保证往返无歧义。
- 位置、生命周期、死亡、传送、显隐及摄像机信息是否完整，取决于录像、补丁和解析器。未知必须显式显示，禁止将未知当作隐藏或精确还原。gem-dota 描述了实体可见性数据，但也明确它不能重建任意点迷雾或地形遮挡：[项目说明](https://github.com/whanyu1212/gem-dota)。

## 首版范围和交互

1. 在现有比赛页增加“战术回放”区域：播放/暂停、0.5×/1×/2×/4×、进度条、当前游戏时间与完整时长、前后跳 5 秒、事件点击跳转；结束时停止，切换比赛时取消旧计时器。
2. 鼠标拖动平移，滚轮以指针为中心缩放，双击或按钮恢复全图；点击英雄选中并跟随，手动拖动退出跟随。坐标变换和点击命中均使用同一个相机模型。
3. 展示有证据的英雄、兵线/野怪、眼位和已有事件；图层可切换。单位标记清楚区分队伍和类型，缺失、过期或解析截断时提示数据不可用。**首版不承诺玩家原始镜头、真实战争迷雾、技能动画、音效、装备外观或原客户端 HUD。**
4. 时间条支持跳到现有击杀、目标和眼位事件。悬浮提示显示采样来源、间隔和插值状态；无可靠轨迹时不凭空补画。
5. 地图提供版本与校准状态，未校准时醒目标注示意图。首版不展示精确视野边界或通行性。

## 技术设计

### 解析与存储

先用现有 gem-dota 建立单独的回放提取器，测试 `ReplayParser.on_entity` 的实体字段、生命周期和解析速度，不修改现有分析口径。英雄先以 **5 Hz 目标采样**做原型，小兵维持 2 秒或按性能实验调整；这是工程目标，不保证源数据每次都有更新。记录原始 tick、可用的高精度游戏时间、实体 `(index, serial)`、类别、队伍、坐标、创建/删除及可验证的死亡/传送标记。记录覆盖范围、缺失区间、解析错误和截断位置。

采用按比赛独立、可重建的 SQLite 缓存，和既有 `review.sqlite3` 分离；保存录像 SHA-256、缓存 schema 版本、解析器版本、地图/补丁证据和采样参数。以 `(entity_id, tick)` 为键并为 tick 建索引，批量事务写入临时文件，完整验证后原子替换；失败保留旧缓存并报告错误。不要因为缓存生成失败破坏已有导入结果。缓存重建、删除及旧缓存版本升级均提供明确入口。先实测一整场的大小与耗时再确定默认采样，不预设容量。

建立 tick 到暂停感知游戏时间的映射与暂停区间索引。播放内部使用录像 tick 或等价的单调录像时间；UI 显示游戏时间。游戏时间跳转在暂停的多解情况明确选择暂停区间起点并在 UI 标识，另提供事件 tick 精确跳转；纯游戏时间模式默认跳过暂停，不能假称复现暂停时长。解析器缺少精确映射时禁用相关精度声明。

### 渲染与播放

新增 `dota_review/replay_cache.py`、`replay_playback.py` 和 `replay_view.py`（名称可随实现调整）。缓存层负责生成与读取，播放层维护单调时钟、速度、时间转换和状态，视图层管理 Tk Canvas、相机、命中与图层；不在 UI 线程解析录像。数据读取使用后台线程、只读连接及窗口预取；Tk 控件更新只在主线程执行，异步请求用代次编号丢弃过期结果。

对连续有效样本进行有界线性插值；缺失超过约定阈值、实体删除、死亡复活、传送、坐标突变或不确定生命周期时停止插值，显示原始样本或缺口。阈值需由实测制定，并保留原始 tick 和推断标识。相机跟随所选单位时，如其位置不可用则保持最后位置并提示，不伪造轨迹。播放节拍使用单调时钟及 `after` 调度，丢帧时按目标时间更新，不累积定时器漂移。

独立客户端外的玩家视角属于后续调研：抽样确认录像中是否存在可归属到指定玩家且连续可用的镜头位置、时间和选择状态，并与客户端画面核对；若不存在或只能部分读取，界面显示“原始视角不可用”，不要以英雄跟随冒充玩家视角。

## 分阶段工作与验收

以下为一名熟悉 Python/Tk 的开发者粗略工作量，依赖录像样本及性能验证，非交付承诺。

| 阶段 | 工作与产出 | 验收门槛 | 粗估 |
| --- | --- | --- | --- |
| 0 可行性样片 | 用至少两场完整、不同补丁录像及一场含暂停或截断录像，测实体字段、镜头字段、地图坐标、耗时与缓存大小 | 英雄轨迹与客户端人工抽查多个时间点；记录可用率、误差及缺口。若无法取得可靠实体坐标则暂停开发 | 1–3 人日 |
| 1 数据层 | 实现版本化独立缓存、tick/游戏时间映射、后台生成、取消与失败恢复；兼容旧比赛重建 | 暂停前后、实体索引复用、截断、重复导入、取消和缓存失效均通过测试；同一 tick 的多实体不丢失 | 3–6 人日 |
| 2 播放器 | 播放、跳转、倍速、平移缩放、跟随、图层和事件跳转 | 一场完整录像可从头播放至结束；多次拖动、切换比赛、暂停与恢复不跳回旧位置；地图坐标与标记命中一致 | 4–7 人日 |
| 3 质量验证 | 性能优化、缺口提示、地图校准和客户端对照 | Windows 目标机器上测完整比赛，记录解析时长、缓存大小、内存、帧率和随机跳转延迟；无 UI 卡死，结果达项目实际确定的阈值后发布 | 2–4 人日 |
| 4 可选探索 | 验证玩家镜头字段，或由用户选择在已安装 Dota 中打开录像 | 每项单独出原型和兼容性记录；不能可靠实现则保持不可用，不影响二维播放器 | 另行评估 |

初始性能目标用于阶段 0 的决策：常见 Windows 机器播放达到约 30 FPS、随机跳转 P95 小于 500 ms、主界面响应不被完整解析阻塞；测出硬件配置和数据规模后调整。完整录像的解析时间和存储预算以实测建立，不用上述目标冒充测量结果。

## 验证清单

- 单元测试：坐标正反变换及缩放锚点；播放时钟和倍速；暂停多 tick 映射；插值断点、实体重用与结束边界；缓存版本及错误恢复。
- 集成测试：以本地小型或经授权的录像夹具验证解析、缓存重建、事件跳转和旧数据库兼容；记录解析器版本和录像哈希，不将大型录像提交源码。
- 手工对照：至少比较开局、团战、传送、死亡复活、暂停、结束等片段；记下客户端时刻、录像 tick、位置误差及未知数据。不要把屏幕插值的流畅程度当作真实性证据。
- 兼容与性能：验证 Windows 窗口缩放、长比赛、反复拖动、缺失文件、损坏录像、取消任务、低内存和补丁更新导致的解析失败。

## 三维探索和资源约束

如果未来仍要求接近原画面，先做限时技术预研：选一个已知版本、一个静态地图区块和一个英雄，分别验证资源读取、坐标/朝向、基础动画、材质和帧同步，再评估单位生命周期、技能粒子、迷雾、皮肤、音效和跨补丁维护。任何一项结果都不能推断整局等价。Source 2 Viewer 的文档表明 VPK 可以浏览及提取，**不等于授权分发资源，也不等于能运行 Dota 渲染逻辑**：[VPK 文档](https://github.com/ValveResourceFormat/ValveResourceFormat/blob/master/docs/guides/vpk-management.md)。
