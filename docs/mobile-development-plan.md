# Dota 2 移动复盘应用：分步开发方案

日期：2026-10-27。本文是可执行的开发计划，功能尚未实现；与已有 [客户端外观看方案](replay-viewer-plan.md) 配合使用。后者的 Tkinter 实现安排用于桌面原型，本方案的移动端使用独立界面和共享数据协议。

## 1. 产品目标与默认假设

让用户在手机上离线查看已分析的比赛，以可交互战术地图观察局势，并随时把想法、问题和改进动作关联到比赛时间，之后检索、复习、导出和回顾。

默认先做**个人离线使用、中文界面、Android 先行、iOS 随后适配**；由于当前工作区是 Windows，iOS 真机编译和发布需要 macOS、Xcode 和相应设备。Flutter 同时支持 Android 和 iOS，[iOS 构建说明](https://docs.flutter.dev/deployment/ios)要求 macOS 与 Xcode。这是便于开工的假设，后续可根据设备和使用方式调整。

优先闭环：**电脑导入 `.dem` → 解析并导出复盘包 → 手机接收 → 回放与分析 → 随手记笔记 → 导出备份/复习**。首版无需账号和服务器，手机离线可用；首次录入比赛依赖 Windows 电脑。手机端直接解析录像和自动云同步是后续阶段，不能当成首版已有能力。

## 2. 功能清单与优先级

| 功能 | 首个可用版 P0 | 完善版 P1 | 远期 P2 |
| --- | --- | --- | --- |
| 比赛获取 | 电脑导出包，手机文件选择导入；离线打开、删除和重新导入 | 局域网传输、断点恢复、批量导入 | 自建服务或可授权数据源、手机本地解析可行性 |
| 比赛管理 | 比赛列表、搜索、最近查看、队伍/日期筛选，缺失和损坏状态 | 英雄、版本、赛事标签与收藏筛选 | 多设备比赛库 |
| 观看 | 二维地图播放/暂停、时间跳转、倍速、双指缩放、拖动、英雄跟随、事件标记 | 多图层、对比与自定义视图 | 经验证的原始镜头或独立 3D 预研 |
| 分析 | 比分/BP、事件、经济、眼位、开雾、神符、轨迹及现有候选分析；标明数据来源和不足 | 跨场趋势、可调阈值、图表联动、版本知识库 | 可解释的高级分析，按能力另立专项 |
| 记录 | 当前时刻一键创建文本笔记、标签、编辑删除、搜索、导出/恢复 | 地图标记与画线、图片/语音附件、模板、任务状态与复习 | 授权协作和云同步 |
| 数据安全 | 本地持久化、手动备份恢复、确认删除、异常恢复 | 可选加密备份和多设备冲突处理 | 账户、共享权限、端到端加密评估 |

战术地图是**基于录像数据重建的二维视图**，不能保证与 Dota 客户端画面、完整迷雾、技能动画、声音或玩家视角一致。跟随英雄是自定义视角，不能称为玩家原始视角。三维和完整客户端效果仅做研究项目，不影响 P0/P1 交付。

## 3. 用户流程与页面

### 3.1 首次使用与导入

1. 电脑导入现有 `.dem`，完成解析后选择“导出手机复盘包”，显示进度、大小、版本与失败原因；原录像默认不进入包。
2. 用户通过文件分享、USB 或其他系统支持的方式把包传给手机；手机用系统文件选择器打开，校验格式、容量、版本和内容完整性。
3. 首次导入写入临时目录，通过校验后才提交到比赛库。已存在相同录像时提示“已导入”，提供保留或更新数据；更新只替换可重建的比赛内容，**不得覆盖笔记**。导入异常或中断时保留原数据并清理临时文件。
4. 手机打开比赛详情；无网络时仍可查看已导入的全部内容。比赛包只含现有采样数据时，地图应显示对应采样密度及能力限制。

### 3.2 导航结构

- **比赛**：搜索和筛选、比赛卡片、最近查看、导入入口、存储占用；详情包含结果、BP、时间轴和解析状态。
- **复盘**：上方地图，下方可折叠时间轴及事件列表；横屏可扩大地图。播放、前后跳转、速度、图层与跟随控制保持可触达。拖动时间时显示预览时间并在松手后更新；事件/笔记点击可跳转。
- **分析**：经济曲线、阵容、眼位、开雾与神符、英雄轨迹、现有联动/拉野候选；选择对象或事件可跳转对应时间。无证据的模块展示“数据不足”，不显示伪造的 0。
- **笔记**：全局列表按比赛、英雄、标签、时间、状态筛选；比赛内显示时间顺序。支持从笔记返回比赛对应时刻。
- **我的/设置**：数据来源、存储与缓存、导出备份、恢复、隐私、帮助、版本信息和故障诊断。

### 3.3 随手记录与改进闭环

观看时固定提供“记录”按钮：点击后自动带入比赛、当前 tick（可用时）、游戏时间、选中英雄及相机位置；先输入一句话即可保存，不强制填写类别。编辑器自动保存草稿，键盘或系统中断后可恢复。笔记支持“观察 / 问题 / 改进动作 / 其他”、自定义标签、文本和创建/修改时间；改进动作可设待练习、进行中、已完成，并可回填结果。

P1 增加地图标点与自由画线（保存世界坐标、颜色和图层）、系统选择图片及手动录音；权限在用户触发时申请，拒绝权限仍能写文本。提醒、周期复习是可选功能，用户明确启用后再请求通知权限。

## 4. 现有代码如何复用

| 现有部分 | 处理方式 |
| --- | --- |
| `ingest.py`、gem-dota、`entities.py` | 留在 Windows/Python 侧，复用解析及实体证据；新增高频回放提取需验证，不能由现有秒级库反推 |
| `storage.py` | 保留桌面数据库；增加只读导出适配器和版本化包格式，移动端使用独立数据库，不直接同步整个桌面库 |
| `core.py`、`draft.py`、`export.py` | 在电脑端计算并导出结果和证据；移动端先展示既有结果，避免两种语言重复实现规则造成口径不一致 |
| `bp.py`、`trends.py`、`patchnotes.py` | P1 按需输出结果和来源；BP 沿用训练集、时间切分及校验门槛，不合格时展示“预测数据不足” |
| `app.py` | 保留现有 Tkinter 桌面端；新增导出入口。手机 UI 使用 Flutter，不能直接运行 Tkinter |
| `teams.py` | 当前导入明确限制指定战队，首版保持现状并在界面提示；若需要个人及任意比赛，后续单列需求和测试，不能假设已有支持 |

现有英雄位置按整数游戏秒去重，小兵/野怪每 2 秒采样，地图为示意底图；不能声称画面逐帧准确。分析结果必须保留现有时间、采样、推断与版本限制。录像导入目前接受 `.dem`，对其他压缩格式不作首版承诺。

## 5. 技术架构与数据协议

```text
Windows: .dem → 现有 Python 解析/分析 → 回放提取器 → 导出 .dreview
                                                    ↓ 文件传输
手机: 包校验/迁移 → 本地比赛库 + 只读回放数据 → 二维播放器/分析
                         ↕
                    独立本地笔记库 → 用户手动备份/恢复
```

**技术选择**：Flutter/Dart 做移动界面与二维 Canvas；手机使用 SQLite 存比赛索引和笔记；大体积轨迹按比赛保存在独立只读 SQLite 文件并按时间窗口读取。Flutter 的 [SQLite 持久化文档](https://docs.flutter.dev/cookbook/persistence/sqlite)可作为实现参考。Python 继续作为首版解析器，不要求手机嵌入 Python。依赖版本在实际建工程时锁定并记录许可。

### 5.1 复盘包 v1 草案

`.dreview` 为 ZIP 容器，包含 `manifest.json`、`analysis.json`、可选 `timeline.sqlite` 和经授权/允许分发的地图资源或资源标识。每个文件以清单记录路径、字节数和 SHA-256；校验和只检测意外损坏，**不证明来源可信**。路径采用相对路径；不包含本机绝对路径、`.dem`、API 凭证及未经用户选择的个人信息。

`manifest.json` 最少包含：`format_version`、`package_id`、`replay_sha256`、`match_id`（可空）、生成时间、解析器与算法版本、录像解析状态与截断位置、地图和版本证据、时钟映射能力、各数据层采样间隔与覆盖范围、文件列表和校验和。`analysis.json` 按稳定 ID 保存玩家、BP、经济、事件、眼位、候选分析及 evidence/source，时间含游戏时间及可用的原始 tick；缺失值为 null 并附原因。轨迹按 `(entity_index, serial, tick)` 建索引，保留生命周期、来源和缺口；版本和字段以协议文档及样例固定后实现。

导入器限制文件数量、压缩后/解压后大小及压缩比，拒绝绝对路径、`..`、符号链接、重复路径、异常数据库和不支持的版本；在隔离临时目录内校验并设置剩余空间检查，通过后原子提交。SQLite 以只读方式访问，不执行来自包中的任意 SQL 或代码。针对损坏、压缩炸弹、恶意路径、磁盘不足和中断编写测试。

### 5.2 时间、画面与笔记一致性

内部优先使用单调录像 tick；展示暂停感知游戏时间。暂停时同一游戏时间可能对应多个 tick：事件及笔记优先按 tick 跳转，仅有游戏时间时按约定跳到区间起点并提示精度。早期包缺乏 tick 映射时，支持秒级跳转并标明限制。连续样本允许有界插值；传送、生命周期变化、死亡/复活、长缺口和不确定状态停止插值。证据不足时显示缺口，不生成真实迷雾。

笔记独立于比赛缓存，使用 UUID、录像哈希、可空 match ID、tick/游戏时间、作者设备、正文、标签、状态、坐标、创建/修改时间和修订号。即使删除比赛，也应先提示并默认保留笔记为“比赛不可用”；重新导入相同哈希后恢复关联。删除笔记提供撤销或回收站。数据更新不得因导入新包覆盖笔记。

### 5.3 备份与以后同步

P0 提供单独的版本化笔记备份包，包含笔记、标签、状态、草稿及后续附件的清单/哈希；默认不包含录像与比赛包。通过系统文件选择器保存和恢复，恢复前预览并提供合并或另存选项；按 UUID 和修订识别重复，存在不同修改时保留两份并要求用户解决，不按时间静默覆盖。中断或无空间时事务回滚。明确提示系统卸载可能移除本地数据，并提供可验证恢复的手动备份。

P1/P2 若做云同步，另行设计账户授权、传输加密、设备标识、操作日志/墓碑、离线重试、冲突副本、备份恢复和删除传播；先定义服务器权限、成本和隐私政策再实现。不要把本地备份称作跨设备自动同步。

## 6. 按顺序开发：每一步的任务和完成条件

工作量是单名熟悉 Python 和 Flutter 的开发者粗估，包含基础测试，不包含等待账号、Mac、商店审核或未知格式故障；阶段 0 的实测可能改变估算。

### 第 0 步：锁定样本和验收基线（2–4 人日）

1. 准备至少两场完整、不同补丁的真实录像，以及一场含暂停或截断的录像；记录哈希、权限、比赛时间和解析器版本，不提交大文件。
2. 测量现有解析耗时、峰值内存、数据覆盖、轨迹采样间隔及地图位置；与客户端人工对照开局、团战、传送、死亡和暂停。
3. 确认 Android 真机、最低系统版本、测试设备和 iOS 的 Mac/真机获取方式；明确当前指定战队范围。
4. 产出基准记录和可用字段清单。**门槛**：至少一场可完成解析；若轨迹/时钟不能满足回放，降级为事件时间轴并先修数据，不进入播放器承诺。

### 第 1 步：拆出导出协议并做端到端样包（3–5 人日）

1. 定稿 `docs/mobile-package-format.md`、最小样包及协议版本；创建 Python 导出模块与 CLI，例如 `python -m dota_review export-mobile MATCH_KEY`，CLI 实际参数以实现为准。
2. 从现有存储读取比赛、分析、原始 tick 和缺失状态；删除本机路径，按清单打包、计算哈希；失败时不留下可误认成功的文件。
3. 写 Python 测试：重复导出、空字段、损坏/截断、版本、文件路径和数据对照。
4. **完成条件**：样包可独立校验，至少一场比赛的 BP、事件和经济与现有桌面输出一致；此时轨迹仍可为现有秒级数据，标记其精度。

### 第 2 步：建立移动工程与离线导入（4–7 人日）

1. 新建 `mobile/` Flutter 工程，按页面、领域模型、数据库、包导入和回放划分模块；配置 Android 构建、格式化、静态检查及自动测试。
2. 设计手机本地库迁移、文件选择、包校验、临时目录及原子导入；实现重复导入、取消、错误反馈、比赛列表和详情。
3. 在 Android 真机完成离线传包导入及重启恢复；测试低存储、损坏和恶意包。
4. **完成条件**：断网后仍能打开比赛详情；更新包不删除笔记数据；异常导入不破坏已有比赛。

### 第 3 步：笔记和备份先闭环（4–7 人日）

1. 实现笔记表、UUID、草稿自动保存、文本/标签/类型、全局列表、搜索、编辑、删除及撤销。
2. 在比赛详情加入记录入口，绑定当前时间；比赛删除后保留笔记并可重新关联。
3. 实现笔记备份、恢复预览、重复识别及冲突副本；模拟进程被终止和磁盘不足。
4. **完成条件**：断网记录、退出重启、备份到另一设备并恢复后内容和关联时间保持一致；损坏备份不覆盖原数据。

### 第 4 步：高密度回放数据与时间映射（5–10 人日）

1. 实测 gem-dota 实体回调，新增独立提取器，试验英雄 5 Hz、小兵较低频率；存 tick、实体身份、坐标、生命周期、缺口及精度。采样率为试验目标，按资源消耗调整。
2. 保存暂停区间与 tick/游戏时间映射，建立时间索引及分块读取；旧比赛提供可取消的重新生成入口。
3. 比对真实录像，测存储体积、解析耗时和坐标误差；建立不连续/传送和实体复用测试。
4. **完成条件**：原始样本、暂停和截断与客户端抽查结果一致到已记录的采样精度；不能验证的字段标记未知。生成失败不影响原比赛及笔记。

### 第 5 步：手机战术播放器（6–10 人日）

1. 实现地图坐标变换、屏幕命中、双指缩放、平移、适配横竖屏、选择和跟随；底图显示版本及校准状态。
2. 实现单调播放时钟、播放/暂停、0.5×/1×/2×/4×、拖动、事件跳转、时间窗口预取、取消过期请求及缺口提示。
3. 实现英雄、兵线/野怪、眼位和事件图层，插值按证据约束；笔记按钮捕获当前 tick 与画面位置，笔记可返回原时刻。
4. **完成条件**：完整录像可播放至结束；暂停、传送、死亡、重复拖动、后台恢复及旋转不导致时间错乱；地图标记和笔记跳转一致。

### 第 6 步：分析页面与联动（5–9 人日）

1. 展示 BP、事件时间线、经济图、眼位/神符/开雾和现有联动及拉野候选；从任一结果进入对应地图时刻。
2. 显示采样、数据来源、候选/推断、版本推定与解析截断；保留现有机制中“后续事件不等于因果”等说明。
3. 补充空数据、较长比赛、跨暂停及旧包兼容测试；与桌面端逐项比较。
4. **完成条件**：同一比赛手机与桌面分析数值及证据一致，缺失不会被显示为确定事实。

### 第 7 步：P0 真机验收和内测（4–7 人日）

1. 在低、中档 Android 真机测试完整用户闭环，记录型号、系统、录像规模、包大小、导入时间、峰值内存、帧率与跳转延迟。
2. 起始性能目标：常规片段约 30 FPS、随机跳转 P95 < 500 ms；同时实测电池和温度，不满足时先降采样、分块或减少图层。具体硬件及最终阈值在第 0 步确定。
3. 检查断网、锁屏、旋转、来电/进程终止、损坏包、删除恢复、重复导入及多次备份；完成可访问性、触控尺寸和字体缩放检查。
4. **完成条件**：无阻断性数据丢失；内测者能独立完成导入、回放、记录和恢复。输出测试记录与已知问题。

### 第 8 步：完善版与 iOS（另估 12–25 人日）

1. P1 增加地图标注、附件、任务复习、跨场趋势、英雄补丁知识与高级筛选；每项先定义数据证据和存储预算。
2. 用 macOS/Xcode 构建并在 iPhone/iPad 真机验证文件导入、手势、后台中断及备份；修复平台差异。
3. 按需实现局域网传输：设备配对、短期凭证、加密传输、断线重试、进度和取消；接收端仍按不可信包校验。不要默认暴露无认证局域网服务。
4. 为发布准备隐私说明、第三方依赖和资源许可、测试分发与商店材料；参考 [Apple 审核规则](https://developer.apple.com/app-store/review/guidelines/)。**完成条件**：两平台核心闭环通过真机测试，附件和传输中断不丢失已有笔记。

### 第 9 步：可选专项，单独立项

- 手机直接解析 `.dem`：比较 Dart/原生解析器或服务端解析，实测内存、电量、耗时与补丁维护；评估平台后台限制，提供取消和恢复，不能保证系统持续运行。参考 [Android 长任务](https://developer.android.com/develop/background-work/background-tasks/persistent/how-to/long-running)及 [Apple 后台策略](https://developer.apple.com/documentation/backgroundtasks/choosing-background-strategies-for-your-app)。
- 原始玩家镜头：逐录像确认字段、连续性、玩家归属并与客户端对照，缺失时明示不可用。
- 自动同步/团队协作：先设计身份、权限、冲突、撤销和成本，再验证私密笔记与共享范围。
- 三维原画面：按已有观看方案限时验证资源及引擎可行性，不承诺完整还原或分发 Valve 素材。

## 7. 发布前质量门槛与风险

P0 合计约 **29–49 人日**（第 0–7 步），这是顺序粗估，不是保证交期。最主要不确定性为录像格式/补丁变动、真实地图资源许可、解析性能、玩家视角字段及移动设备内存。每阶段需以真实样本重新估算；协议、数据和测试通过后才进入下一步。

发布检查：自动化测试覆盖包安全和迁移、时钟映射、插值断点、数据丢失与备份冲突；在真机完成无网络、较长录像、系统中断及低存储测试；记录已知地图和分析限制。默认不采集笔记、录像或使用数据；若以后接入网络分析、AI、账户或协作，先说明实际数据流并实现用户控制。游戏资源和商标的使用、再分发及数据来源条款需在公开发布前逐项核实。

## 8. 下一次开发从哪里开始

按第 0 步选录像和设备，完成测量记录；随后只做第 1 步的协议、样包与 Python 导出，建立可重复测试。协议确定后再建立手机工程。开发时每完成一步保留代码、迁移及验证记录，让下一步能直接接续。
